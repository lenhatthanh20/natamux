This walk-through uses the desktop app and one agent. Starting a task and reaching the first approval takes about ten minutes, and most of that is the agent working. The rest depends on your task and your agent: the default pipeline waits for you once, at the spec, then an agent implements and another agent reviews the work. You need the [requirements](/docs/getting-started/install/#requirements) and a git repository you can experiment in.

## Add a project

Open Natamux. The app starts its daemon and opens the dashboard, already signed in. On the first launch there is no project and no task yet, so the main area shows **Welcome to Natamux** with three steps, and the sidebar says **No projects yet**.

<Steps>

1. Click **Choose folder…** in step 1 and pick the top folder of the repository, the one that holds `.git`. Natamux adds it at once. If the folder is not a git repository, you see the reason in a message.
2. Sign in to the agents you want. Step 2 lists the command of each agent. Click the copy button, run it once in any terminal and sign in. See [Agents](/docs/agents/).
3. Click **Open workflow settings** in step 3 to choose the stages of the project and the agent of each one. You can do this later.

</Steps>

You can also click **Type a path…** to open the projects dialog, where you type the folder or pick it with **Browse…**. **File → Add Project…** (`Cmd+Shift+O` on macOS, `Ctrl+Shift+O` on Linux) opens the same dialog.

Add more projects the same way, at any time.

<Aside>
Running the dashboard in a browser instead? Open it and paste the token into the **Daemon token** field. It is `NATAMUX_TOKEN` of the daemon, or the token the daemon printed when it started. The browser keeps it for this address only.
</Aside>

## Start a task

You have two ways to start.

- **Add a task** puts an idea in the backlog. Type a title in the field "Add a task to the backlog" (press `n`) and press Enter.
- **Start a task** starts work right away. Click the **+** button in the title bar, or press `c`.

For this guide, use **Start a task**.

<Steps>

1. Enter a **Title**, for example `Fix the login redirect`.
2. Pick the **Project** to work in.
3. Pick an **Agent**, or "No agent, a plain terminal".
4. Click **Start task**. Natamux makes the task at once and opens it. It shows **Preparing workspace** while it makes a git worktree and a branch, which can take minutes in a big repository. Then it starts the agent in the task's terminal.

</Steps>

<Figure src="/screens/native/start-task" width={1600} height={900} alt="The native Start a task dialog with the visible title Clamp checkout totals after discounts. Context from is My notes, Project is storefront, Branch from is main, Agent is Claude Code and Task flow is Full flow." caption="The native Start a task dialog keeps the title, context, project, branch, agent and task flow together." />

The dialog has three groups. **Task** is what the agent reads as the task's context; the line under it says what that is for the source you pick. **Workspace** is where the task runs, and the line under it names the branch Natamux makes. **Agent** is who runs it and how; the line under it lists the stages of a full flow. The note left of **Start task** says what is still missing, or what Natamux will make.

<details>
<summary>Every field of the dialog</summary>

| Field | What to enter |
|---|---|
| Context from | Where the context comes from: **My notes**, **A GitHub issue**, or **An agent skill** when an agent has a skill. It shows when there is more than one source |
| Skill | With **An agent skill**. Click **Pick a skill** and choose the skill that reads the context |
| Notes | Optional, with **My notes**. What to change and why, where to look, and how to tell it is done |
| Reference | With any other source. The issue, ticket or record to read, for example `#42` |
| Attachments | Optional. Screenshots, logs or specs. Click **Add files**, drop them, or paste a screenshot |
| Project | The project to work in |
| Create a worktree | On by default. Off: the task works in the project folder itself, on the branch checked out there, with no worktree and no new branch. Only one open task can work there at a time. Removing its workspace only detaches it: the folder, its changes and its branch stay |
| Branch from | The branch to start from. It defaults to the default branch, such as `main`. Natamux fetches it first, so the task starts from its newest commit. **Remote branches** has the branches of `origin`, also ones you never fetched |
| Branch | The name of the new branch. It follows the title, such as `natamux/ABC-123-fix-the-login-redirect` for "ABC-123 Fix the login redirect". Type your own name to change it; the reset button next to it makes it follow the title again |
| Agent | Pick an agent, or "No agent, a plain terminal" |
| Task flow | **Full flow** runs the project's stages. **One agent** gives the whole task to one agent in Terminal 1 |

</details>

If you added a task to the backlog first, open it and click **Start agent** (or **Start task** with no agent if you only want a terminal).

## Watch the agent work

Open the task. The **Terminal** tab shows the agent running in the task's worktree.

<Figure src="/screens/native/task-review-shell5" width={1600} height={900} alt="A native task workspace with three terminal panes: Terminal 1, Test spec in Terminal 10, and Review running in Terminal 12. The Progress panel shows Test spec and Implement completed before Review." caption="Three native task terminals beside the workflow. Review runs in its own terminal. Terminal output is scripted." />

On the dashboard, the state of the task updates by itself, because Natamux's hooks tell it when the agent works, asks or finishes. You can close the dashboard and the agent keeps running.

## Answer when it needs you

When an agent asks a question or waits for a permission, the task moves to **Needs input**. Its row in the sidebar becomes a card with the agent's question. In the native app the question stays in the terminal and **Progress** marks the waiting stage. The browser dashboard also shows a count such as "1 needs you" in its title bar.

<Steps>

1. Click the task in the sidebar.
2. Click **Answer** on its card in the sidebar.
3. Type your answer in the terminal.

</Steps>

The task goes back to running. See [Dashboard](/docs/guides/dashboard/).

## Review the stage

Each task moves through stages. The **Progress** tab of the details panel shows them and the evidence of each one, beside the terminal.

<Figure src="/screens/native/task-spec-approve" width={1600} height={900} alt="A native task waiting at Spec. The stage card says In review, shows two checks passed, and offers Show evidence, Approve, Skip and Send back. The terminal shows the scripted demo agent report." caption="Spec waits for review in the native app. Approve it from the stage card. Terminal output is scripted." />

When a stage waits for you, the task is in review. Read what the agent produced, then:

- **Approve** moves on to the next stage.
- **Send back** returns the task to an earlier stage, with a note about what should change.
- **Skip** leaves the stage out.

With the default pipeline you approve once: the spec.

- After you approve the spec, the task's agent implements it in Terminal 1.
- When it is done, a review agent reads the changes in Terminal 5.
- If the review finds problems, it sends the task back to Implement by itself, at most two times.

See [The review loop](/docs/concepts/review-loop/) and [Stages](/docs/concepts/stages/).

## Look at the changes

Open the **Changes** tab. It lists the changed files and shows a diff for each one, side by side or inline. The **History** tab shows the task's branch as a graph.

<Figure src="/screens/native/changes-generate" width={1600} height={900} alt="The native Changes view with a side-by-side diff of checkout.py, two changed files on the right, an empty commit-message field, and Generate, Commit all, Push and Create PR controls." caption="The native Changes view, with a side-by-side diff and an empty commit-message field." />

## Commit, push and open a pull request

<Steps>

1. In the **Changes** tab, write a commit message, or click **Generate** to let the agent draft one. Then click **Commit all**. It commits every change, new files included.
2. Click **Push** in the task header. The button shows how many commits are ahead, for example **Push ↑2**.
3. Click **Create PR**. It needs the `gh` command, logged in. When the pull request exists, the button becomes **Open pull request**.

</Steps>

Natamux never pushes or merges unless you click the button or run the command.

## Finish

Merge the pull request on GitHub. While a dashboard is open, Natamux checks pull requests of open tasks once a minute (every 5 minutes once all their checks have finished), and when one is merged it moves a task in review to done.

To clean up, open the task and remove its workspace. Natamux asks first. If the worktree has changes that are not committed, it lists them, and in the app you can still remove it anyway, which discards them.

<Aside type="tip" title="You did it">
One task went from a title to a pull request, with an agent and your approvals. Next, shape the process to your team.
</Aside>
