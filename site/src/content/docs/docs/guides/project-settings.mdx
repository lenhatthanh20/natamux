Each project has its own settings: the [stages](/docs/concepts/stages/) every task goes through, where task context comes from, the issue tracker and how agents ask for permission. Natamux keeps them in `.natamux.json` at the root of the repository, so you can commit the file and share it with your team.

Open them from the sidebar: click the gear next to the project. Or right-click the project, or click **...** next to it, and choose **Settings**. The page header shows the project's name, the path of `.natamux.json` under it, and three tabs at the right: **General**, **Stages** (the default) and **JSON**. The arrow keys move between the tabs. While the JSON is not valid, **General** and **Stages** are off and say "Fix the JSON first".

## The General tab

The tab has three groups: **Agents** (the first two fields), **Git** (the branch name) and the issue choices. Each field shows a dot (outline: the default, filled: changed) and, when changed, a reset icon that clears it.

- **Agent send backs.** The most times an agent, or a CI failure, may send the task back from one stage before it waits for you (`agents.maxSendBacks`). Empty means no limit, the default. See [Limit the send backs](#limit-the-send-backs).
- **Pause idle agents after (minutes).** After how many minutes an agent that ended its turn, in a terminal nobody looks at, is paused (`agents.pauseIdleAfterMinutes`). Empty means 30. `0` turns the pause off. See [An idle agent pauses](/docs/guides/terminal/#an-idle-agent-pauses).
- **Branch name.** The name of the branch of a new task (`git.branchName`). Empty means `natamux/{id}-{slug}`.

### GitHub issues

**Open a GitHub issue for a task** sets when Natamux opens a GitHub issue for a task (`tracker.createIssue`). By default it opens none: **Manual** opens one only when you click **Create issue** in the task's Progress view. **On Spec approved** opens it when you approve the Spec stage (without a Spec stage, when the pull request opens), and **Just before PR opens** just before the pull request opens. **Never** also hides the **Create issue** button.

Under the choices, the tab says what the issue is made of. With `tracker.type` set to `none`, the choices are turned off. See [Open an issue for a task](/docs/guides/github/#open-an-issue-for-a-task).

## The Stages tab

- **Pipeline.** A flow chart in a dashed box on top shows the stages as you edit them, with side-by-side stages in one column. It scrolls sideways, and down when a branch has long notes. A person icon marks a stage that waits for your approval. A pencil marks a prompt of your own. A stage on its own agent shows that agent's icon and its model (or the agent's name) under its name. Click a node to open its stage.
- **Stages.** One list of every step, with the count in its title. A stage row has a drag handle, a tile for its kind, its name, marks (waits for you, a prompt of your own, **Custom**, a problem), what it runs ("Codex · Auto", "Waits for you"), a switch that turns it on or off, and a **...** menu: **Edit…**, **Move up**, **Move down**, **Run alongside the stage above** or **Run on its own**, and **Remove**. Click a row to open the stage. Drag a row, or focus it and press `Alt+ArrowUp` or `Alt+ArrowDown`. A stage that is off stays in the file with its prompt and approval, but new tasks do not get it.
- **Groups and branches.** Stages that run side by side sit under a line with the group name. A branch has an **If** row, then each path with its condition and its stages. A path without stages shows "No stage yet" and **Add**, which lists the stages that fit there.
- **+ Add.** One button above the list opens a menu: **Built-in stage…**, **Custom stage…**, **Branch…** and **Side by side…**. Each opens a dialog. A new stage goes before Release; a new branch goes after the selected step.
  - **Built-in stage…** shows the catalog of 28 stages, grouped by phase: Understand, Design, Build, Check and Ship. Type to search, move with `ArrowUp` and `ArrowDown`, and press `Enter` or click a stage to add it. The dialog closes and the new stage opens. The [catalog](/docs/reference/configuration/#stage-catalog) lists every stage.
  - **Custom stage…** makes a stage of your own: **Name**, **Id** (made from the name until you type one), **Kind** and, for an agent stage, **Output file**.
  - **Side by side…** opens **Run stages side by side**: pick 2 to 4 agent or manual stages that are not in a group yet, with an optional **Group name**. Stages of one group must share a place: the top level, or one path of a branch. They move next to the first of them and start together.
- **Edit a group.** Open a group's **...** menu: **Edit group…**, **Move up**, **Move down** and **Remove**. **Edit group…** opens the same dialog with the group's stages checked. **Split group** runs each of them on its own, in order.
- **Built-in or custom.** A stage of your own has a **Custom** tag and a cyan tile in the list, and a solid ring in the flow chart. Its stage dialog says "A stage of your own".
- **Edit a stage.** Clicking a stage opens its dialog: its tile and name, and **Basic** and **Advanced** at the top right. **Basic** holds the name, approval, the agent, ending its terminal and the prompt. **Advanced** holds arguments, command, check command, output file, required sections, finished when, workflow, CI and a terminal of its own; its label says "N changed" or "all default". A stage with a problem in an **Advanced** field opens on **Advanced**. Edits go to the draft at once; **Done** (`Mod+Enter`) closes the dialog, **Remove** removes the stage after a question. Nothing is saved until you click **Save** on the page.

| Field | Shown for | Meaning |
|---|---|---|
| **Name** | Every stage | The name in the dashboard. |
| **Wait for my approval** | Every stage | A dot shows whether it is the default (outline) or changed (filled). When changed, the reset icon (**Use default**) goes back. A `review` or `manual` stage is always on, with "Always on for this kind of stage." For `release` the label is **Open the pull request when I click**. |
| **Tasks can run it as a workflow** | Agent stages | Gives each task a **Run with a workflow** checkbox on this stage. On by default for Plan and Implement. See [Run a stage as a workflow](/docs/concepts/stages/#run-a-stage-as-a-workflow). |
| **Tasks can check it on CI** | Testing stages and agent stages without an output file | Gives each task a **Check on CI** checkbox on this stage. On by default for Implement and Automated tests. See [Check a stage on CI](/docs/concepts/stages/#check-a-stage-on-ci). |
| **End the agent and close its terminal when the stage is done** | Context, agent and testing stages outside Terminal 1 | Off by default. When the stage is done, Natamux ends its agent or command and closes its terminal. A stage in Terminal 1 shows "This stage runs in Terminal 1, which cannot be closed." instead. See [End a stage's terminal](/docs/concepts/stages/#end-a-stages-terminal). |
| **Run in a terminal of its own** | Agent stages with an output file outside a group. Any other stage whose file sets `ownShell`, such as a stage in a group or a stage of another kind, shows it too, so you can clear it | Checked: the stage runs in Terminal 5 with a new session, apart from the task's agent in Terminal 1. Unchecked: it runs in Terminal 1 with the task's agent and its session. On by default for Test spec, Review, Security review, Performance check and Accessibility check. Unchecking it also clears the stage's **Agent** and **Arguments** when the stage can no longer have its own agent. See [Stages in their own terminal](/docs/concepts/stages/#stages-in-their-own-terminal). |
| **Agent** | Stages that start their own agent: agent stages beside the stage in Terminal 1, such as Test spec, stages in their own terminal, such as Review, and agent or testing stages of your own | The agent this stage starts. **Task's agent** keeps the task's own. A stage with its own agent or arguments runs in a terminal of its own, from Terminal 6, and Terminal 1 keeps the task's agent. See [Choose a model](/docs/concepts/stages/#choose-a-model). |
| **Arguments** | The same stages, and any stage whose file sets `args` | Words added to that agent's command line, such as `--model sonnet`. On a stage that does not use them, the field says so; clear it to remove it. |
| **Prompt** | Agent and testing stages | The chips `{title}`, `{description}`, `{dir}` and `{ref}` insert placeholders; `{id}`, the task id, also works when typed. **Insert skill** opens a picker with the groups **Project**, **Plugins** and **Only on this machine**, and inserts `{skill:<name>}`. A prompt of your own gets no commit rule: say whether the agent commits. |
| **Command** | Testing stages, and any stage whose file sets `command` | The command to run. **Lint and types** and **End-to-end tests** need one. On another kind of stage it does not run; clear it to remove it. |
| **Check command** | Every stage | A shell command the daemon runs in the task's folder after the stage reports done, such as `pnpm typecheck`. Exit code 0 passes. Empty: none. |
| **Output file** | Agent stages | The Markdown file the stage writes. Fixed for a catalog stage. |
| **Required sections** | Agent stages with an output file | Headings the file must have. |
| **Finished when** | Every stage | The sentence the progress view shows before the stage starts. |

- **Problems.** Each problem shows on its stage's row, and **Save** is off until they are fixed. The rules are in [Rules for the pipeline](/docs/reference/configuration/#rules-for-the-pipeline).
- **Bottom bar.** One line under every tab: **Unsaved changes** or **Saved**, the problem and warning counts, a **...** menu with **Reset to default**, **Import…** and **Export**, then **Discard** and **Save** (`Mod+Enter`). Under the list, a note says "New tasks use this pipeline. Tasks on their way keep their stages, but use the new prompts and approvals." **Reset to default** puts the default pipeline in the editor: Context, Spec, Implement, Review and Release. See [Import and export](#import-and-export).

**Save** changes only `stages` and `agents.maxSendBacks`. Other fields and keys it does not know stay in the file. When the stages equal the default pipeline, Save leaves `stages` out of the file, so the project follows later changes of the default.

## The JSON tab

The **JSON** tab edits the whole file as text. Edits move between the tabs. JSON that is not valid keeps you on this tab with the error shown, until you fix it. Use it for fields the **General** and **Stages** tabs do not show:

- `requireCommit`, `requireClean` and `check` on a stage;
- `context.sources`, such as a skill or MCP source with a name of its own;
- `tracker.type` and `tracker.linkInPr`, the rest of the issue tracker;
- `agents.permissionMode`, `auto` or `ask`.

Every field is in the [configuration reference](/docs/reference/configuration/).

## Import and export

Use these to copy settings from one project to another, or to keep a copy.

- **Export** downloads what the screen shows, edits included, as `<project>.natamux.json`. It is turned off while the **JSON** tab holds JSON that is not valid.
- **Import…** opens a `.json` file (up to 1 MiB) in the screen, in place of the current settings. When the file has a **Check command**, **Command** or **Arguments** on any stage, it asks first and lists each one, with its stage, in full: they run on this computer. With edits not saved, it asks too, in the same question. It does not save: check the settings, then click **Save**. A file with a problem opens on the **JSON** tab with the error.

To use an exported file in another project, import it there, or copy it into the repository as `.natamux.json`.

## When the file changes

- If the file changed on disk since you opened the screen (another editor, a pull), Natamux says "The file changed on disk since you opened it." **Reload** reads the file again and drops your edits. **Overwrite** saves your version over it.
- Closing the screen with edits asks "Discard your changes?".
- If the file is not valid, the screen shows the error and the default settings, and **Save** asks before it replaces the file.
- The daemon reads the file again when it changes, so an edit in your own editor counts at once.

## Common changes

### Choose the review agent

<Steps>

1. Click **Review** in the stage list. Its dialog opens.
2. In **Agent**, pick the agent, for example **Codex**.
3. Optional: on **Advanced**, in **Arguments**, add words such as `--model sonnet`.
4. Click **Done**, then **Save**.

</Steps>

<Figure src="/screens/native/stage-agent-picker" width={1600} height={900} alt="The Agent menu for Review in native Project settings, listing Claude Code, Codex, Gemini CLI, GitHub Copilot, Cursor and the scripted demo agents. demo-reviewer is selected, and Arguments is empty." caption="Choose a stage agent from the menu. The scripted demo-reviewer agent is selected here." />

Review runs in its own terminal, Terminal 5, so it can use another agent than the task's without touching the session in Terminal 1. **Test spec** works the same way, in Terminal 2. See [The review loop](/docs/concepts/review-loop/#choose-the-review-agent).

### Split the pipeline by a condition

<Steps>

1. Click **+ Add**, then **Branch…**, and give it a **Branch name**.
2. Give each path a **Path name** and a condition, such as **File has text** (a section of `plan.md`) or **Command succeeds**. **Add path** adds one, up to 4.
3. Click **Add branch**. Nothing changes in the pipeline until then; **Cancel** drops the branch.
4. In the list, each path of the branch shows "No stage yet" and **Add**. Click **Add** to give it stages.
5. Click **Save**.

</Steps>

<Figure src="/screens/native/stages-branch" width={1600} height={900} alt="The Edit branch dialog for Bug or feature in native Project settings: the Branch name, then one card per path, Bug fix with a context.md text condition and Feature marked Otherwise." caption="A branch in native Project settings: one card per path, each with its condition." />

To change a branch later, click its **If** row or its node, or choose **Edit branch…** in its row's **...** menu. **Save branch** writes the changes; **Cancel** leaves the branch as it was.

See [Paths with a condition](/docs/concepts/stages/#paths-with-a-condition) and [Build a workflow](/docs/guides/workflows/).

### Give a stage another agent

Click the stage and set **Agent**, and **Arguments** on **Advanced**. The stage then runs in its own terminal. See [Mix agents in one task](/docs/guides/mix-agents/).

### Have a person read the diff

Click **+ Add**, choose **Built-in stage…**, pick **Manual review** in the Check phase, and drag it after **Review**. The task then waits for your **Approve** before **Release**. To make the agent review wait for you as well, tick **Wait for my approval** on **Review**.

### Skip the planning

Turn off **Plan** with its switch. After you approve the spec, Test spec and Implement start at once.

### Add a check stage

Pick **Security review**, **Performance check** or **Accessibility check** from the catalog. Each one writes a report with a **Findings** section and waits for your approval. Like Review, it runs in **Terminal 5**, the one terminal that all such stages share. When an agent still runs there, for example the Review agent, the stage gets its prompt in that session. With its own **Agent** or **Arguments**, it runs in a terminal of its own instead, from Terminal 6.

### Run your own test command

Click **Automated tests** and, on **Advanced**, enter a **Command**, such as `pnpm test`. A terminal runs it instead of an agent. Exit code 0 passes the stage.

### Limit the send backs

By default an agent may send a task back as often as it likes. When two agents keep disagreeing, give them a limit:

<Steps>

1. On the **General** tab, type a number in **Agent send backs**, for example `2`.
2. Click **Save**.

</Steps>

The next send back past the limit is refused, and the task waits for you in **Needs input**. Clear the field to remove the limit. See [The review loop](/docs/concepts/review-loop/#limits).

### Let agents ask before they act

On the **JSON** tab, add:

```json title=".natamux.json"
{ "agents": { "permissionMode": "ask" } }
```

Each agent then follows its own permission settings. See [`agents`](/docs/reference/configuration/#agents).

## Approve the project's commands

A project can run commands on your machine: a stage `check`, a stage `command`, a path condition `when.command`, the words of a stage `args`, and the setup script (`.natamux-setup`, `.natamux-setup.ps1`). Natamux runs them only after you approve them, and again after each change. A project with none of them needs no approval.

- After you add a project, a dialog lists every command word for word, with where it comes from, and the setup script. Choose **Approve** or **Not now**.
- **Start a task** in a project that is not approved shows the same dialog. The task starts after either button.
- Until you approve, the project settings show **Commands not approved** with a **Review commands** button that opens the dialog.
- Approval also lets the agents trust the worktree and run in auto mode. So the repository's own agent config (`.codex`, `.cursor`, `.claude`, MCP servers) runs too.
- A save of the settings in this screen approves the commands you saved. A changed setup script still needs the dialog.
- Projects added before this check came in were approved as they were at the first start.

While a project is not approved:

- A stage with a `check` or a `command` fails with **Repo commands are not approved. Review them in the project settings, then retry.** A branch whose path runs a command fails the stage before it the same way.
- The setup script does not run. The task's log says **Setup script skipped**.
- Agents start without auto mode and without their trust of the folder, and stage `args` are left out.

Stage `args` are split at spaces, and each word is quoted, so no shell sign in them runs. A quoted value with spaces becomes several words.

Without the app, use [`natamux repo trust`](/docs/reference/cli/#repo-trust).

## What a change does to tasks

- New tasks use the new pipeline.
- A task on its way keeps its list of stages. It uses the new names, prompts, approvals and checks of those stages.
- A catalog stage that is gone from the file keeps its catalog settings for a task on its way.
